## Question 1. For each of the four statements, which constraint blocked it and why?

### 1.1
```sql
INSERT INTO team (name, headquarters)
VALUES ('Avengers', 'Los Angeles');
```

- **Constraint:** `UNIQUE`
- **Why:** The team name `Avengers` already exists in the `team` table. Because `team.name` is defined as `UNIQUE`, PostgreSQL rejects the duplicate value.

### 1.2
```sql
INSERT INTO hero (name, team_id)
VALUES ('Ghost', 99);
```

- **Constraint:** `FOREIGN KEY`
- **Why:** `team_id = 99` does not refer to an existing row in `team`. The foreign key on `hero.team_id` requires the referenced team to exist.

### 1.3
```sql
INSERT INTO hero (age)
VALUES (30);
```

- **Constraint:** `NOT NULL`
- **Why:** The `hero.name` column is defined as `NOT NULL`, but this INSERT does not provide a value for `name`.

### 1.4
```sql
DELETE FROM team
WHERE id = 1;
```

- **Constraint:** `FOREIGN KEY`
- **Why:** Team `1` is still referenced by heroes such as Tony and Natasha through `hero.team_id`. The foreign key prevents deleting the referenced parent row while dependent rows still exist.

## Question 2. Why is the foreign key on `hero` and not on `team`?

The `team`–`hero` relationship is **one-to-many**: one team can have many heroes, while each hero belongs to at most one team.

In a relational database, the foreign key is therefore placed on the **many side**, which is `hero`. Each hero row stores one `team_id` value referring to its team.

Putting the foreign key on `team` would require one team row to store a collection of many hero IDs, which does not fit the normal relational-table design.

## Question 3. Sketch the tables you need for the many-to-many relationship.

A many-to-many relationship between heroes and missions requires **three tables**: `hero`, `mission`, and a link (junction) table.

### `hero`
- `id` — `PK`
- `name` — required column

### `mission`
- `id` — `PK`
- `title` — required column

### `HeroMissionLink`
- `hero_id` — `FK` → `hero.id`
- `mission_id` — `FK` → `mission.id`
- `PRIMARY KEY (hero_id, mission_id)` — composite primary key

The composite primary key ensures that the same hero cannot be assigned to the same mission more than once.

## Question 5. Why is `id` typed `int | None` with `default=None`, when every row in the database has an id?

When a new `Hero` or `Team` object is created in Python, it does not have a database-generated ID yet, so its `id` is initially `None`.

After the object is inserted into the database, PostgreSQL generates the ID and SQLModel can load that value back into the Python object.

Therefore:

```python
id: int | None = Field(default=None, primary_key=True)
```

means that the ID is temporarily allowed to be `None` before insertion, even though every stored database row eventually has an integer ID.

The following `Hero` attributes become database columns:

## Question 7. Compare the `CREATE TABLE hero` printed by SQLAlchemy with the one written by hand in Part 1.

The SQLAlchemy-generated table should represent the same basic structure as the handwritten table, but there are several differences caused by the SQLModel field definitions.

### Main differences

1. **Column types**
   - Python `str` fields are mapped to string database types such as `VARCHAR`.
   - Python `int` fields are mapped to integer types such as `INTEGER`.
   - Optional fields can be nullable.

2. **`NOT NULL`**
   - Required fields are generated as `NOT NULL`.
   - Optional fields such as `age` and `team_id` can be `NULL`.

3. **Primary key**
   - `id` is created as the table's `PRIMARY KEY`.
   - The ID is generated by the database when a new row is inserted.

4. **Foreign key**
   - `team_id` is created with a foreign-key relationship to `team.id`.

5. **Indexes**
   - Fields declared with `index=True` can cause SQLAlchemy/SQLModel to create database indexes.
   - The handwritten Part 1 table did not explicitly create these indexes.

6. **Constraints**
   - Constraints such as `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, and `FOREIGN KEY` come from the SQLModel field definitions and relationships.

The exact SQL and index names depend on the model definitions and the SQLAlchemy/SQLModel-generated DDL shown in the terminal.

## Question 8. Stop and restart the server. Is `CREATE TABLE` printed again? Why? What does `create_all` do when a table already exists?

`create_all()` does not recreate a table that already exists.

`SQLModel.metadata.create_all(engine)` checks the database schema and creates only tables that are missing. Therefore, after restarting the server, an already-existing table such as `hero` is skipped.

It does **not** drop the existing table or recreate it from scratch.

## Question 10. Comment out `session.commit()` in `create_hero` and create a hero. What happens?

Without:

```python
session.commit()
```

the INSERT transaction is not committed to the database, so the new row is not durably stored in PostgreSQL.

`session.add(obj)` only adds the object to the SQLAlchemy session; it does not by itself commit the transaction.

`session.refresh(obj)` is used after the database operation to reload values from the database, especially values generated by the database such as the new primary-key `id`.

Therefore, the normal create sequence is:

```python
session.add(hero)
session.commit()
session.refresh(hero)
```

The exact HTTP response after removing `commit()` depends on the endpoint code and what happens to the session afterward, but the important point is that the row is not committed to the database.

## Question 11. Which SQL statement does `echo=True` print for PATCH with body `{"age": 17}`? Does it update every column or only `age`? Why?

SQLAlchemy prints an `UPDATE` statement whose changed values include the `age` column, conceptually like:

```sql
UPDATE hero
SET age = ...
WHERE hero.id = ...
```

It does not need to update every column because the PATCH handler uses:

```python
hero_in.model_dump(exclude_unset=True)
```

This keeps only the fields that the client actually supplied. Therefore, when the body is:

```json
{"age": 17}
```

only `age` is changed.

## Question 13. Call `GET /heroes?min_age=18&team_id=1` and copy the SELECT printed by `echo=True`. Where do the values `18` and `1` appear? Why is this safe against SQL injection?

The values `18` and `1` are supplied to the SQL statement as **bound parameters/placeholders**, rather than being concatenated directly into the SQL string.

The exact placeholder syntax depends on the SQLAlchemy/psycopg output, but conceptually the query is like:

```sql
SELECT ...
FROM hero
WHERE hero.age >= :min_age
  AND hero.team_id = :team_id
```

with the actual values bound separately.

This is safe against SQL injection because the parameter values are treated as **data**, not as executable SQL code.

## Question 14. Why filter in the database instead of using a Python list comprehension?

Filtering in the database is more efficient because the application does not have to load every row into Python before filtering.

For example:

```python
[h for h in session.exec(select(Hero)).all() if h.age >= 18]
```

first retrieves all matching table rows into application memory.

By using:

```python
select(Hero).where(Hero.age >= 18)
```

the database performs the filtering and returns only the required rows.

This reduces unnecessary data transfer and memory usage and allows the database to use its query-optimization and indexing mechanisms.

## Question 17. Is there a `power` column? What happens to `GET /heroes` and why? Why is dropping all tables and running `create_all` again not an acceptable fix in production?

There is **no `power` column yet** if the model was changed but no migration has been applied.

After adding:

```python
power: str | None = None
```

to the model, restarting the application does not automatically alter the existing PostgreSQL table.

When `GET /heroes` tries to query the updated model, the application can fail because the database table does not contain the `power` column expected by the model.

Dropping all tables and running `create_all()` again is not an acceptable production solution because dropping the tables destroys existing data.

The correct solution is to use a **database migration**, such as Alembic, to add the new column while preserving existing data.

## Question 18. What does `upgrade()` and `downgrade()` do in Alembic?

### `upgrade()`

`upgrade()` contains the migration operations that move the database schema **forward** to the new revision.

For the `power` example, it adds the new `power` column.

### `downgrade()`

`downgrade()` contains the reverse operations that move the database schema **backward** to the previous revision.

For the `power` example, it removes the `power` column.

In other words:

```text
upgrade   → apply the schema change
downgrade → undo the schema change
```

## Question 19. Where does Alembic store which revision the database is at? Why should the `migrations/` folder be committed to Git?

Alembic stores the current database revision in a special table named:

```text
alembic_version
```

The `migrations/` folder should be committed to Git because it contains the migration history and the scripts needed to reproduce schema changes.

This allows other developers and deployment environments to apply the same database changes in the correct order using Alembic.

## Question 20. Rename `secret_name` to `alias` and run `revision --autogenerate` (do not apply it). What did Alembic generate? Why is that dangerous for existing data, and how would you fix the script?

When a column is renamed in the model, Alembic autogeneration may interpret the change as:

1. Drop the old `secret_name` column.
2. Add a new `alias` column.

For example, the generated migration may contain operations conceptually like:

```python
op.drop_column("hero", "secret_name")
op.add_column("hero", ...)
```

This is dangerous because dropping `secret_name` removes the existing values stored in that column. Creating `alias` afterward does not automatically copy the old data into the new column.

The migration should therefore be **reviewed and manually edited** so that the database performs a column rename instead of a drop-and-add operation.

Conceptually, the desired change is:

```text
secret_name  →  alias
```

while preserving the existing data.
